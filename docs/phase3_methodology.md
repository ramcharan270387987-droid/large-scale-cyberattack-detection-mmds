# Phase 3 analytics methodology

The private CPU notebook attaches the saved Phase 2 producer as a Notebook Output input. The pipeline locates the mounted validation receipt by the SHA-256 recorded in the Phase 2 manifest. It verifies the dataset release, cleaning version, file bytes, Parquet footers, ten partition days and the clean and feature-ready label totals. It compares label mappings and temporal eligibility counts across both layers, checks the timestamps against capture day and fails before analytics when a critical check differs. The raw-aligned layer is read for selected cleaning comparisons. [Phase 2 Parquet manifest](../manifests/parquet_layers.json)

## Query populations

- **All rows** cover 10 source-day partitions with original record multiplicity. Frequency tables retain the original label and use the approved family mapping. The family-by-day table includes explicit zero cells for absent observed families.
- **Event-time rows** retain the stored eligible subset. Hours and three-hour windows use local wall-clock values. Windows have fixed boundaries at 00, 03, 06, 09 and subsequent three-hour marks, separately per capture day. An absent hour means the query had no eligible rows for that hour. The source timezone is unverified.
- **Feature comparisons** use available finite observations. Directional packets and bytes are summed per flow when both terms are available. Sample standard deviation uses `stddev_samp`. Reported Pearson correlations use pairwise complete observations for eight specified pairs. Duration and inter-arrival times are expressed in µs, volume in packets or bytes, and flow rates per second.
- **Quantiles** use Spark `percentile_approx` with accuracy 4,096 at P10, P50, P90 and P99. Its documented relative rank-error parameter is approximately 1/4,096, and percentile values can vary with repeated values or steep distribution tails. Counts, finite-value supports and extrema are direct aggregates. Floating-point sums and means follow Spark's arithmetic.
- **Patterns** use benign-reference P99 and P10 cutoffs from this same corpus. Strict exceedance is used for high rates, counts, bytes and inter-arrival time. The short-and-large rule combines duration at or below P10 with bytes above P99. Eligible denominators and per-family counts are reported for each rule. This is retrospective exploration with observed labels and scenario effects.
- **Quality checks** compare raw versus clean nonfinite values, initial-window sentinels, finite means and nulls. The exact-content count uses the saved multiplicities. The feature-label conflict count uses Phase 2's cleaned shared feature key. Neither diagnostic alters the default cohort.
- **Ports and flags** are observational transport context. Port tables retain the top 12 within each binary class and family and include the denominator. TCP flag tuples use positive counts on protocol 6. Differences across days or labels can reflect capture composition, lab scheduling and class prevalence.

## Execution and reproduction

`scripts/build_phase3_notebook.py` bundles the exact pipeline and Phase 2 manifest into the notebook. Submit through the existing Kaggle web-API wrapper with `kernel_sources` pointing to the Phase 2 producer. Persisted logs are available through the notebook status and logs endpoints. Retrieve the compact archive with `scripts/retrieve_phase3_evidence.py` and regenerate the reports with `scripts/render_phase3_report.py`. The repository stores CSV aggregates, JSON validation and execution-plan evidence, static PNGs and documentation.

The SQL pipeline projects the required analytic columns and caches that projection on disk for repeated workloads. Each SQL result has a compact collection limit and a checkpoint. The benchmark warms both APIs, alternates their order for three paired measurements and checks the full day-by-label counts after each execution. Timings include Spark job execution and compact collection. They describe this workload and environment. The bounded RDD comparison uses a deterministic digest sample of the smallest capture by source bytes. Physical plans and RDD lineage are saved with the results.

If a worker runs out of resources, retain its query checkpoints and rerun the unfinished work as separate traffic/distribution, quality or benchmark batches against the same verified mount. Reconcile daily, family and eligible-hour totals before assembling an output report. Use the reference-threshold checkpoint for the dependent pattern query.
